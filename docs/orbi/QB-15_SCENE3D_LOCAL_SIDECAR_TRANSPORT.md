No ORBI Creative Studio file is modified by QB-15.

## Purpose

QB-15 implements the provider-neutral local process transport proposed by QB-14.

The transport allows an Electron main process to talk to the Python ORBI Scene3D runtime without:

- opening a public/local TCP listener,
- importing Qwen in the product repository,
- exposing Python or SQLite to the renderer,
- giving the renderer reconciliation mutation authority.

## Transport

Protocol:

```text
orbi.scene3d-sidecar/v1
```

Framing:

```text
stdin  → one JSON object per line
stdout → one JSON response per line
stderr → diagnostics/provider logs
EOF    → normal process shutdown
```

Maximum inbound frame:

```text
262144 bytes (256 KiB)
```

Oversized lines are drained without buffering the whole remaining frame and return:

```text
SIDECAR_MESSAGE_TOO_LARGE
```

## Stdout integrity

Stdout is reserved exclusively for JSONL protocol frames.

Runtime/provider stdout is redirected to stderr during:

- lazy runtime construction,
- ORBI runtime execution.

This prevents a provider diagnostic `print()` from corrupting the Electron↔sidecar protocol.

## Sidecar operations

Exactly:

```text
status
scene_info
object_info
dry_run_recipe
execute_recipe
pending_recoveries
reconciliation_history
```

Not exposed:

```text
reconcile
retry
release_reservation
execute_python
execute_blender_code
set_provider
set_ledger_path
```

## Status behavior

`status` is local and does not initialize Blender/Qwen.

It reports:

- protocol version,
- operation surface,
- transport = `stdio-jsonl`,
- public listener = false,
- automatic R2 retry = false,
- reconciliation mutation = false,
- durable ledger schema,
- reconciliation schema.

This allows Electron main to inspect basic pilot readiness even when Blender is unavailable.

## Recovery inspection

These operations read SQLite directly and do not start the provider runtime:

```text
pending_recoveries
reconciliation_history
```

Reconciliation mutation remains outside the sidecar and stays operator-only under QB-13.

## Scene3D mapping

### `scene_info`

Maps to:

```text
orbi.scene3d.v1 / scene_info
```

### `object_info`

Maps to:

```text
orbi.scene3d.v1 / object_info
```

Input accepts only:

```text
object_name
```

### `dry_run_recipe`

Input accepts only:

```text
recipe_id
parameters
```

The sidecar injects:

```text
dry_run = true
```

server-side.

The caller cannot supply or override `dry_run`.

### `execute_recipe`

Input accepts only:

```text
recipe_id
parameters
```

The sidecar forwards the Electron-main-generated request id unchanged into `OrbiRequest`.

Fields such as:

```text
code
provider
dry_run
```

are rejected at the transport boundary.

## Request ownership

QB-15 assumes the QB-14 rule:

```text
request_id generated by Electron main
```

The sidecar validates and preserves it.

The sidecar does not generate replacement ids and does not retry failed R2 operations.

## Error layering

There are two different success/failure layers.

### Transport success

```json
{
  "ok": true,
  "result": {
    "ok": false,
    "error": {
      "code": "PROVIDER_FAILURE"
    }
  }
}
```

means:

- JSONL request was valid,
- sidecar processed it,
- ORBI application/provider operation failed.

### Transport failure

```json
{
  "ok": false,
  "error": {
    "code": "SIDECAR_PROTOCOL_ERROR"
  }
}
```

means the message itself was invalid or the sidecar could not dispatch it.

This separation prevents protocol errors from being confused with Blender/provider failures.

## Lazy provider startup

The Blender/Qwen runtime is constructed only when a Scene3D read or execution operation needs it.

Recovery inspection and status remain usable without provider startup.

Within one sidecar process, runtime construction happens once and is reused.

## Post-QB-14 SQLite initialization hardening

During the first QB-15 stacked preflight, the accumulated suite exposed a real startup race inherited
from the earlier durable-ledger implementation:

```text
sqlite3.OperationalError: database is locked
```

The race occurred before request reservation logic: concurrent fresh ledger instances both executed
`PRAGMA journal_mode=WAL` while opening the same new SQLite database.

QB-15 hardens this by:

- keeping `busy_timeout=10000` on every connection,
- keeping `synchronous=FULL` on every connection,
- treating WAL mode as persistent file-level configuration,
- performing WAL negotiation only during initialization,
- retrying only transient SQLite `locked` initialization failures with bounded backoff,
- failing fast for all other operational errors,
- adding an 8-thread fresh-ledger initialization regression.

This hardening does not weaken replay semantics or reservation atomicity. The original
`BEGIN IMMEDIATE` reservation path remains unchanged.
